# Комплексная оптимизация загрузки и раздачи SyncWatch (Low-RAM Architecture)

Комплексный план внедрения надежной чанковой загрузки файлов с поддержкой паузы и возобновления, а также высокопроизводительного HTTP 206 стриминга с околонулевым расходом оперативной памяти сервера (Zero-Copy Disk I/O) под условия ограниченных ресурсов сервера.

> [!IMPORTANT]
> **Подтвержденные решения на основе ваших ответов:**
> 1. **Минимальное потребление RAM**: Сервер не хранит видео в оперативной памяти Node.js. Раздача построена на прямом считывании из дискового кэша ядра ОС (Linux Page Cache) через оптимизированные стримы с автоматическим закрытием дескрипторов при отключении зрителя.
> 2. **Чанковая дозагрузка (Resumable Uploads)**: Клиент нарезает файл на чанки по 5 МБ через `File.slice()`, поддерживает ручную и автоматическую **Паузу**, **Возобновление** при обрыве связи и отображение мгновенной скорости (МБ/с).

---

## 1. Overview & Core Concept

- **Что делает**: Превращает загрузку тяжелых видеофайлов (1–10+ ГБ) в отказоустойчивый процесс: пользователь видит прогресс по частям, скорость передачи, оставшееся время, может ставить передачу на паузу или продолжать после сетевого сбоя. Сервер сохраняет каждый чанк напрямую в файл на диске, расходуя не более 64–256 КБ RAM на поток. Раздача клиентам оптимизирована под параллельные Range-запросы с корректным backpressure.
- **Целевая аудитория**: Зрители совместных киносеансов с разными скоростями домашнего интернета и недорогими серверами/VPS с небольшим объемом оперативной памяти (512 МБ – 2 ГБ RAM).
- **Ключевая ценность**: Загрузка больше не срывается на 99% из-за одного кратковременного сбоя сети; сервер никогда не падает с `JavaScript heap out of memory`, а видео воспроизводится у всех участников синхронно без рывков.

## 2. User Experience & Visual Design

### 2.1. Ключевые сценарии пользователя (UX Flows)

1. **Запуск загрузки большого фильма**:
   - Хост перетаскивает файл (или выбирает через диалог).
   - Сразу открывается аккуратная карточка активной загрузки: название файла, общий размер, индикатор прогресса (полоса с делениями по чанкам).
   - Отображаются живые метрики: *Скорость* (например, `14.2 МБ/с`), *Передано* (`450 МБ / 1.4 ГБ`), *Осталось* (`~01:08 мин`).
2. **Пауза и возобновление (Manual Pause / Network Recovery)**:
   - Хост может нажать кнопку **«Пауза»** (например, чтобы освободить домашний канал), передача плавно останавливается на текущем чанке.
   - По кнопке **«Продолжить»** клиент запрашивает у сервера `/api/rooms/:roomId/upload/status/:fileId` и продолжает ровно с того байта, где остановился.
   - Если интернет кратковременно пропал, включается авто-повтор (до 5 попыток с нарастающей задержкой) без сброса уже переданных данных.
3. **Мгновенная готовность к просмотру**:
   - Как только последний чанк записан, сервер атомарно регистрирует трек в плейлисте комнаты, файл сразу становится активным, и все зрители начинают предзагрузку.

### 2.2. Визуальный стиль и компоненты
- **Карточка загрузки в плейлисте**:
  - Строгий темный фон `bg-neutral-900/90` с аккуратной рамкой `border-neutral-800`.
  - Динамический прогресс-бар с тонким акцентом `bg-rose-500` и индикацией буфера.
  - Кнопки управления: компактные иконки `Pause`, `Play` (возобновить), `X` (отменить) с всплывающими подсказками.
  - Никаких громоздких плашек — чистая типографика: моноширинные цифры таймкодов и скорости (`font-mono text-xs text-neutral-400`).

## 3. Key Product Decisions & Trade-Offs

- **Архитектура чанков (Slices)**:
  - *Выбор*: Размер чанка по умолчанию 5 МБ.
  - *Почему*: 5 МБ — оптимальный баланс между сетевыми накладными расходами HTTP-запросов и объемом данных, который теряется при внезапном сбросе соединения.
  - *Альтернатива*: Tus-протокол или WebSocket-бинарники. Отклонены из-за утяжеления зависимостей и избыточных накладных расходов памяти на сервере.
- **Политика RAM-менеджмента на сервере**:
  - *Выбор*: Потоковая запись чанков через файловый дескриптор `fs.openSync` / `fs.write` по смещению (`offset`) без накопления в массивах Node.js.
  - *Почему*: Сервер потребляет фиксированные миллисекунды CPU и считанные килобайты памяти на запрос вне зависимости от размера видео (хоть 10 ГБ).
  - *Альтернатива*: Хранение частей в `Buffer.concat()` в RAM. Приведет к `Out of Memory` на недорогих серверах.
- **Очистка временных файлов (Garbage Collection)**:
  - При отмене загрузки или закрытии комнаты временные файлы `.part` удаляются мгновенно.

## 4. Technical Architecture & Data Strategy

### 4.1. Схема системы (Architecture & Data Flow)

```
┌────────────────────────────────────────────────────────────────────────┐
│                          БРАУЗЕР (Клиент)                              │
│                                                                        │
│  [ Файл 2 ГБ ] ──> File.slice(5MB) ──> [ Очередь чанков ]              │
│                                            │                           │
│  ┌─────────────────────────────────────────┼─────────────────────────┐ │
│  │ Контроллер загрузки                     │                         │ │
│  │ • Пауза / Старт / Отмена                │                         │ │
│  │ • Расчет скорости (МБ/с)                ▼                         │ │
│  │ • Авто-повтор при сбое                  POST /upload/chunk        │ │
│  └───────────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────┬───────────────────────────┘
                                             │ HTTP (5MB Slices)
                                             ▼
┌────────────────────────────────────────────────────────────────────────┐
│                          EXPRESS СЕРВЕР (Node.js)                      │
│                                                                        │
│  /upload/chunk ────────> fs.createWriteStream(..., { flags: 'r+' })   │
│                          Запись по offset в /storage/.../temp.mp4      │
│                          Расход RAM: < 128 КБ на запрос!              │
│                                                                        │
│  /upload/status/:fileId > Проверка размера уже записанного файла       │
│                                                                        │
│  Финальный чанк ───────> fs.renameSync(temp, final.mp4)                │
│                          Socket.io: broadcast('playlist:update')       │
└────────────────────────────────────────────┬───────────────────────────┘
                                             │ Range: bytes=start-end
                                             ▼
┌────────────────────────────────────────────────────────────────────────┐
│                        РАЗДАЧА ЗРИТЕЛЯМ (HTTP 206)                     │
│                                                                        │
│  • fs.createReadStream(..., { start, end, highWaterMark: 128 * 1024 }) │
│  • Прямой pipe в response (Zero-Copy)                                  │
│  • stream.destroy() по событию req.on('close')                         │
│  • Заголовки: Accept-Ranges, Content-Range, Cache-Control              │
└────────────────────────────────────────────────────────────────────────┘
```

### 4.2. Новые API-эндпоинты сервера
1. `GET /api/rooms/:roomId/upload/status/:fileId`
   - Возвращает `{ uploadedBytes, totalBytes, isCompleted }`. Позволяет клиенту узнать, с какого байта продолжить передачу при повторном открытии или после паузы.
2. `POST /api/rooms/:roomId/upload/chunk`
   - Принимает бинарный чанк через multipart или raw body со смещением:
     - `fileId`: уникальный ID файла.
     - `fileName`: исходное имя.
     - `chunkIndex`: порядковый номер части (0, 1, 2...).
     - `totalChunks`: общее количество частей.
     - `startByte`: байтовое смещение.
     - `totalSize`: общий размер исходного файла.
   - Записывает чанк по точному смещению в `video_temp.mp4`.
   - Если `chunkIndex === totalChunks - 1`, файл валидируется, переименовывается в постоянный, добавляется в плейлист комнаты и запускается оповещение в комнату.
3. `POST /api/rooms/:roomId/upload/cancel/:fileId`
   - Немедленно удаляет временный файл `.part` и освобождает место на диске.

### 4.3. Оптимизация видео-стриминга (`/stream/:fileId`)
- Тюнинг `highWaterMark: 128 * 1024` (128 КБ) в `createReadStream`: предотвращает переполнение очередей Node.js при множестве медленных зрителей.
- Жесткий обработчик закрытия соединения:
  ```typescript
  req.on('close', () => {
    stream.destroy();
  });
  ```
  Это предотвращает утечку открытых файловых дескрипторов (`EMFILE: too many open files`), если зрители часто перематывают видео или переподключаются.
